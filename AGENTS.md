# AGENTS.md

## Architecture intent

- `App` = user-facing, has a canvas and runs in its own FreeRTOS task
- `Service` = background task, no canvas, runs indefinitely
- Both inherit `KeiraThread` — don't bypass this hierarchy
- `ksystem` is the global entry point to AppManager, ServiceManager, etc.

## Non-obvious conventions

- `K_BTN_*` defines (`keira.h`) are `lilka::Button` enum values — use them for UI components (`menu.addActivationButton(K_BTN_BACK)`, `menu.getButton() == K_BTN_EXIT`), not for reading raw button state
- To read button state, use named fields on `lilka::State` directly: `state.a`, `state.b`, `state.up`, `state.start`, etc. — `State` has no array indexing
- Use `K_FT_*_HANDLER(X)` macros (`keira.h`) for file type dispatch
- Use `StringFormat()` instead of `sprintf()`
- Use `#pragma once` — never `#ifndef` include guards
- Use `defer` (`src/utils/defer.h`) for scope-exit cleanup
- Use `acquire` (`src/utils/acquire.h`) for RAII mutex locking
- Use `KMTX_SETER_GETER` macro for thread-safe getters/setters on shared state

## What not to touch

- `src/keira/keira_version_auto_gen.h` — auto-generated at build time
- `build/` — generated by ESP-IDF
- Submodules under `components/` (see `.gitmodules`) — pinned upstream code, never edit in place; bump the submodule instead
- `components/arduino_tinyusb/` — vendored TinyUSB glue from esp32-arduino-lib-builder
- `components/mJS/` and `components/SimpleFTPServer/` — vendored, don't reformat

## Build gotchas

- Native ESP-IDF CMake project: `make build` (local ESP-IDF) or `make docker-build` (pinned `espressif/idf` image); `make help` lists everything
- ESP-IDF version is pinned per board in `boards/<board>/board.cmake` and enforced at configure time — currently **v4.4.7** with arduino-esp32 **2.0.17** as an IDF component
- Layout: `src/` is the Keira IDF component (`src/CMakeLists.txt`, explicit `REQUIRES`); `components/<name>/` is one component per library — our `CMakeLists.txt` plus the upstream code as a shallow git submodule inside (`components/arduino` and `components/esp-dsp` are submodules that are IDF components themselves)
- `data/spiffs/` becomes the internal filesystem image (`make flash-fs`); `data/img/` and `data/assets/` are repo-only images and design sources
- Bumping the Lilka SDK submodule (`components/lilka/sdk`): also update `LILKA_SDK_VERSION` in `components/lilka/CMakeLists.txt` (configure fails on mismatch)
- A board is a `boards/<board>/` dir with `board.cmake`, `sdkconfig.defaults` and `partitions.csv`; select it with `make BOARD=<board>`
- Build dirs: `build/` (default board, same as plain `idf.py`), `build-<board>/` for others, `<dir>-docker/` for Docker builds — never mix host and Docker builds in one dir
- Local ESP-IDF must be the pinned tag with matching submodules (`git submodule update --init --recursive`) and its own CMake 3.x (`idf_tools.py install cmake`); CMake 4 is rejected at configure time
- sdkconfig is generated in the build dir and is not refreshed from defaults; after changing `boards/<board>/sdkconfig.defaults` run `make fullclean`
- One-off compile flags: `make FLAGS="-DLANG_EN -DFMANAGER_DEBUG"` (`-DKEIRA_BUILD_FLAGS=...` for `idf.py`)
- **v2** (ESP32-S3) is the only supported board; v1 support was removed
- `clang-format` and `cppcheck` are enforced in CI — run `make clang-format` and `make cppcheck` before committing

## Arduino vs esp-idf

- `String` (Arduino) is the only Arduino type allowed — use it for all string handling
- For everything else prefer esp-idf equivalents over Arduino wrappers:
  - `xTaskCreate` / `vTaskDelay` / `SemaphoreHandle_t` over Arduino task abstractions
  - `esp_wifi_*` over `WiFi.*`
  - `esp_http_client_*` over `HTTPClient`
- Use `vTaskDelay()` instead of `delay()`
- `Preferences` is acceptable temporarily until a better storage mechanism is introduced
- `pinMode` / `digitalWrite` are acceptable temporarily until a GPIO abstraction is introduced
- When esp-idf and Arduino both work, esp-idf is preferred

## Lilka SDK

See [Lilka SDK](https://github.com/lilka-dev/sdk) and its `AGENTS.md` for SDK-specific conventions.

## Filesystem

- Always use C-style file API (`fopen`, `fread`, `fwrite`, `fclose`) with canonical paths (`/sd/...`, `/spiffs/...`) — never use `SD.open()`, `SPIFFS.open()`, or any Arduino filesystem wrappers

## Global state

- No global variables in `src/apps/` or `src/services/` implementations
- All state must be members of the `App` or `Service` subclass
- File-scoped constants (`static const` / `constexpr`) are fine — mutable globals are not
